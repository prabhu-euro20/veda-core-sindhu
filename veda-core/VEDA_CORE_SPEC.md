**Design philosophy — "Object-Centric Deterministic Architecture"** (formally named and given by the user, 2026-07-23; supersedes the earlier two-pillar statement below by expanding it to three, not by discarding it — the original security/energy framing is preserved inside pillars 2 and 1 respectively). Not competing on raw throughput. Three pillars:

1. **Object-Centric Design (the soul)**: memory is not "bytes at addresses," it is Objects. Addresses may change; an `Object_ID` never does — this is what gives Veda-Core's design its unique identity. **Already real, not aspirational, in both layers**: `Object-Bind`'s `Rebind` mode (`VEDA_CORE_SPEC.md` §4, real and verified in Sail since Milestone V-A/B, and in RTL since `rtl/MILESTONE_8_RESULTS.md`) is the concrete mechanism that makes this literally true — the MSA can silently relocate an object (`Base` changes), and software's own relative position (`Offset`) and identity (`Object_ID`) never move. RTL Milestone 8 proved this with a real physical address, not just a metadata field: an object was re-populated at a new `Base`, and a capability register's own untouched `Offset` correctly followed it to the new physical location on the very next memory access. See `DESIGN_SOUL_AND_UNIQUENESS.md` for the full, freshly-researched case that this is a deliberate revival of a real architectural branch (system-wide, `Object_ID`-indexed capability tables — Plessey System 250, Cambridge CAP) the rest of the field moved away from decades ago for reasons tied to a throughput/compatibility target this project explicitly does not share.

2. **System Execution Security (hardware-level shield)**: unauthorized access is stopped at the hardware gate, not by software convention, via the MSA — through **Capability ID**, **immutable Tag/lock semantics**, and **atomic transactions**. **Already real and verified, cross-referenced precisely**: Capability ID = the `Object_ID` + 16-entry Capability Register File system (all six RTL milestones, Sail V-A/B/C). The "immutable lock" property = the capability **Tag bit** — out-of-band (not counted in the 128 data bits, §2), never directly writable by software, only ever set/cleared by the hardware's own capability-manipulation logic (`Bind`/`OCA`/`CSetBounds`/`CSeal`/`CUnseal`, all verified) — this is this document's own working interpretation of "immutable lock bits," stated explicitly so it can be corrected if a distinct, new per-object lock mechanism (beyond Tag) was intended. Atomic transactions = Veda-Atomic's 9 real AMO-style ops (RTL Milestones 2/5, Sail V-B) plus the Object-Bind exclusive-ownership policy (§4.1, real UPMEM precedent). The newest addition to this pillar: `EMERGENCY_HANDLING_DESIGN_REVIEW.md`'s decision that an emergency handler starts with a fresh, minimal capability context, never inheriting the interrupted task's live bindings — a direct extension of this same pillar to asynchronous/emergency execution, reasoned from the `CSeal`/`CUnseal` minimal-privilege model already built (Milestone 6).

3. **Deterministic Performance (precision)**: not minimizing average latency — minimizing *jitter*, so every task has a fixed, provable worst-case execution time (WCET). Stated plainly, matching real domain practice: in automotive and robotics, WCET-boundedness is treated as a correctness property, not a performance nice-to-have. **Partially real already, newly recognized as serving this pillar specifically, not previously framed this way**: the ODT's own flat (not multi-level) structure was chosen in §5.1 explicitly so `Object-Bind`'s latency doesn't depend on how deep a given `Object_ID` sits — a determinism-motivated decision made before this pillar was named as such. The cache-less design (pillar-adjacent, inherited from the original energy framing below) also directly serves this pillar for a second, independent reason worth stating: caches are real, extensively documented as the dominant source of WCET-analysis pessimism and timing anomalies in real-time-systems literature — a cache-less design doesn't just save energy, it removes one of the hardest, most-studied sources of timing unpredictability from the analysis problem entirely. **Newest concrete step**: `EMERGENCY_HANDLING_DESIGN_REVIEW.md`'s corrected emergency-handling flow, targeting a small (2-3 cycle), hardware-only, provably-bounded shadow-register capture — zero *software* overhead, a real, explicit, bounded hardware cost, not a "zero-latency" claim (real precedent checked: even CV32RT's best-in-class register-banking result is 6 cycles, never zero). **Real, honest gap**: no WCET analysis/certification tooling exists yet for either layer — a real, unstarted cost, not silently assumed solved by the architecture alone.

*(Original two-pillar statement, preserved for continuity)*: security (every access checked, hardware traps on violation) and energy efficiency (address-less, cache-less — "no addresses, no caches, only Objects"). Simplicity is a first-class goal, not a fallback — every design decision below favors the simpler of two options once security is satisfied.

## 1. ISA Summary

Veda-Core reuses the standard RV64I instruction formats (R-type and I-type) and adds three custom instruction families, all under RISC-V's reserved custom-opcode space (Custom-3 deliberately left unallocated for future growth — this is a repeated, verified lesson from CHERI's own 13-year history of needing more room than initially planned).

| Opcode name | Encoding (verified against Table 65, RISC-V opcode map) | Format(s) | Role |
|---|---|---|---|
| Custom-0 (OCL) | `0001011` | R-type (data ops) + I-type (Object-Bind) | Address-less data movement, NMC dispatch, capability binding |
| Custom-1 (Veda-Atomic) | `0101011` | R-type | Synchronization, AMO-style atomics on objects |
| Custom-2 (Veda-Cap) | `1011011` | R-type | Capability metadata: bounds, permissions |
| Custom-3 | `1111011` | — | **Reserved, unallocated** |

**Custom-3 is unallocated again, and this row was right the whole time.** The RTL once carried one
instruction here, `veda.droppriv` (Milestone 4) -- a one-way privilege drop that this table was never
updated to declare, and that the Sail model never defined at all. R36/R39 retired it: its own recorded
justification was that "real `mret` is a trap-return semantic this core has no trap to return from",
and Milestone 9 built the traps and MRET. **Privilege is now the standard privileged-architecture
mechanism on both layers** -- a trap raises to Machine saving the old level in `mstatus.MPP`, `mret`
restores from it, and software drops privilege by writing MPP and executing `mret`. Every Custom-3
encoding raises Illegal_Instruction. `mstatus` (0x300) implements MIE, MPIE and MPP; the fields with no
consumer on this hart read zero rather than advertising features that do not exist. **A CSR access
below the address's own privilege -- `csrPriv(csr) = csr[9..8]` -- is an illegal instruction, on reads
as well as writes.** See DESIGN_07 R39.

### Custom-0 (OCL) — R-type data operations

Standard R-type layout: `funct7[31:25] | rs2[24:20] | rs1[19:15] | funct3[14:12] | rd[11:7] | opcode[6:0]`.

`rs1` = Capability Register (`c0`–`c15`, pre-bound via Object-Bind). `rs2` = a GPR-held offset for *this access only* — bounds-checked against `rs1`'s `[0, Length)` window (Section 2) and used to compute the real location `rs1.Base + rs2`, but **not** read from or written back into the capability's own persistent `Offset` field. This is deliberately different from `OCA`/Veda-Atomic/`NMC_ADD` below, which *do* use the capability's own stored `Offset` — `OCL`/`OCS` can afford a fresh, transient offset each access because their R-type encoding has a spare register field (`rs2`) for it; Veda-Atomic and `NMC_ADD` don't (their `rs2` is already committed to a value operand), so they depend on `OCA` having positioned the capability's own `Offset` in advance.

`funct7` is the command-type selector: `0000000`=OCL (Load), `0000001`=OCS (Store), `0000010`=NMC_ADD. `funct3` is the width field, but its scope differs per command — **resolved below, with real RISC-V precedent for both halves of the answer**:

**OCL / OCS width table** (`funct3`, mirrors real RISC-V's `LB`/`LH`/`LW`/`LD`/`SB`/`SH`/`SW`/`SD` convention exactly — verified directly from the RISC-V ISA manual's own Load and Store instruction-format diagrams, pp.37 and 44: both the `LOAD` and `STORE` encodings use an identically-named, identically-positioned `funct3 = width` field, with no narrower encoding for stores):

| funct3 | OCL Mnemonic | OCS Mnemonic | Width |
|---|---|---|---|
| `000` | OCL.B | OCS.B | 8-bit |
| `001` | OCL.H | OCS.H | 16-bit |
| `010` | OCL.W | OCS.W | 32-bit |
| `011` | OCL.D | OCS.D | 64-bit |
| `100` | OCL.C | OCS.C | 128-bit (capability load/store) |
| `101` | *(reserved — see Object-Bind below, different format)* | — | — |
| `110`–`111` | reserved | reserved | — |

**NMC_ADD width table** — deliberately *not* the same table. Resolved by direct analogy to real RISC-V's own `Zaamo` (Atomic Memory Operations) extension (verified, ISA manual p.120): AMO's `funct3` width field supports **only W (32-bit) and D (64-bit)** — RISC-V does not define byte- or halfword-width atomic read-modify-write operations at all, since a sub-word atomic RMW has no meaningful hardware realization at the memory-controller granularity most systems atomically operate on. NMC_ADD is architecturally an AMO-class compute-at-memory operation, not a data-movement operation, so it inherits AMO's restriction rather than OCL's full table:

| funct3 | NMC_ADD Mnemonic | Width |
|---|---|---|
| `010` | NMC_ADD.W | 32-bit |
| `011` | NMC_ADD.D | 64-bit |
| others | illegal for NMC_ADD | — |

**NMC_ADD semantics** — resolved by direct adaptation of real RISC-V `AMOADD`'s own ratified semantics (ISA manual p.120: *"AMO instructions atomically load a data value from the address in `rs1`, place the value into register `rd`, apply a binary operator to the loaded value and the original value in `rs2`, then store the result back to the original address in `rs1`"*). NMC_ADD is the object-based, capability-checked analogue of exactly this: `rs1` = Capability Register pointing at the target object location (pre-positioned via `OCA` if needed, see Custom-2 below); `rs2` = GPR holding the value to add; `rd` = GPR that receives the **old** (pre-add) value read from the object, matching AMOADD's return convention exactly. The MSA (Section 5) performs the add — this is a genuine memory-side compute operation, not a round-trip: the CPU already validated bounds/permissions locally before issuing the request, so the MSA's job is purely "read old, add, write new, return old," architecturally identical in spirit to how a real RISC-V SoC's memory controller implements `AMOADD.W`.

**`OCL.C`/`OCS.C` semantics — Milestone 7, resolved this pass.** A real, honest gap found before writing any code: the width table above (`funct3 = 100`) has always named this width "128-bit (capability load/store)," but no prior pass specified what `rd` actually means for it — every other OCL/OCS width treats `rd` as an ordinary GPR (`VEDA_CORE_SPEC.md`'s own text above: `rd` is read as the store-value source for OCS, or written as the load destination for OCL), and a 128-bit capability value cannot fit in one 64-bit GPR.

**Decided, by direct, verified analogy to real CHERI**: CHERI's own primary capability-load/store instructions (`[C]LC`/`[C]SC`, already cited and verified elsewhere in this document, §3) target a *capability register*, not a GPR — a capability's Tag bit and full field set have no meaningful representation in an ordinary integer register. `OCL.C`/`OCS.C` follow the identical real precedent: `rd` (bit position `[11:7]`, the same slot every other OCL/OCS width already uses) is reinterpreted, for this one width value only, as a 4-bit Capability Register index (`c0`–`c15`, top bit of the 5-bit field reserved/expected-0) — exactly the same "one shared field position, meaning reinterpreted per encoding" idiom this document's own Cross-cutting design principle (below) already establishes for every other instruction family, not a new one invented for this case. For `OCL.C`: `rd` is the *destination* capability register (the loaded capability, with its Tag set only if the memory-resident tag says so — see below). For `OCS.C`: `rd` is the *source* capability register (the one being stored), mirroring `OCS.D`'s own existing "rd = value source" role exactly, just holding a capability instead of a GPR value.

**The Tag bit's real memory representation — the actual reason this instruction needed its own design pass, not just a width extension.** A capability's Tag is explicitly out-of-band, "not counted in the 128" (§2) — so storing a capability to memory and loading it back must preserve that Tag *alongside* the 128 data bits, without letting software forge a Tag bit by writing arbitrary bytes to memory and then loading them back as if a real capability had always lived there. This is the exact problem real CHERI hardware solves with **tagged memory** — a real, physically separate tag bit per capability-aligned memory granule, checked/set only by capability-load/store logic, never plain byte loads/stores. `OCL.C`/`OCS.C` adopt the identical principle: a real, additional, out-of-band **tag store**, addressed by 16-byte-aligned granule, exactly mirroring how the Tag bit is already kept separate from the capability register's own 128 data bits (§2's own "Tag(1, out-of-band)... not counted in the 128"). A plain `OCL.D`/`OCS.D`/`OCA`/etc. access to the same bytes never touches this tag store at all — only `OCL.C`/`OCS.C` do, matching CHERI's own real, documented separation between ordinary data loads/stores and capability loads/stores.

**Scope boundary, stated honestly, not silently assumed**: the tag store is not modeled over the full, unbounded address space — it covers the same real, ELF-loadable RAM region every other Veda-Core mechanism already operates within (the `elfmem`/real object-backing region, `Base=0x8001_0000`-class addresses already used throughout the ODT's own seeded test entries). This mirrors the exact, already-stated, already-verified scope-boundary discipline this project used for the RTL ODT itself (`rtl/MILESTONE_PLAN.md`: "sized to 256 entries for this milestone... real silicon-area consciousness... explicitly deferred, later work, not attempted here") — a real, bounded, honestly-scoped mechanism, not a claim of unbounded generality.

### Custom-0 (OCL) — I-type: Object-Bind (`funct3 = 101`)

See Section 4 for full detail. Discriminated from the R-type OCL operations by `funct3 = 101` — legal because `funct3` occupies the same bit position `[14:12]` in both R-type and I-type, so the decoder can determine which interpretation applies before touching the rest of the word.

### Custom-1 (Veda-Atomic) — R-type

```
31        27  26  25   24        20   19        15   14    12   11      7   6        0
[ op(5) ][aq][rl][      rs2        ][      rs1     ][funct3(width)][    rd    ][0101011]
```

- `funct7[31:27]`: 5-bit atomic operation select (mirrors real RISC-V AMO's use of a full 5-bit field for 11 operations — SWAP/ADD/XOR/AND/OR/etc. proposed as the reference operation set, not yet finalized to exact values).
- `funct7[26:25]`: `aq`/`rl` ordering bits, identical role to real AMO.
- `rs2`: value operand (swap value / add value).
- `rs1`: Capability register — **must already point at the exact target location** (adjust first via `OCA`, defined under Custom-2 below — resolved, previously an open gap).
- `funct3`: width, reusing the OCL B/H/W/D/Cap convention.
- `rd`: destination register for the old value.

### Custom-2 (Veda-Cap) — R-type

```
31                    25  24      20   19      15   14    12   11      7   6        0
[   funct7 (op-select)  ][   rs2    ][   rs1    ][funct3(dest-kind)][   rd    ][1011011]
```

- `funct7`: 7-bit operation select.
  - `0000000`–`0000110`: `CGetBase`, `CGetLen`, `CGetPerm`, `CGetTag`, `CGetType`, `CGetAddr`, `CGetOffset` (metadata queries, one `funct7` value each — this was the direct fix for the original design's collapsed "one funct3 = Query" problem, which couldn't say *which* field was being queried). Per the `Base`/`Length`/`Offset` field fix (Section 2): `CGetBase` returns `Base`, `CGetLen` returns `Length`, `CGetOffset` returns `Offset` alone, `CGetAddr` returns `Base + Offset` (the real, resolved location) — this three-way split was already implied by this query list existing before the field-table fix; the fix made the field table consistent with instructions that were already named here.
  - `0001000`: `CSetBounds`
  - `0001001`: `CSetBoundsExact`
  - `0001010`: **`OCA`** (Object Capability Adjust) — resolved a previous pass, see below.
  - `0010000`: **`CSeal`** — resolved this pass, see below.
  - `0010001`: **`CUnseal`** — resolved this pass, see below.
  - `0010010`: **`OCInvoke`** — resolved this pass (formerly Section 6 item 7), see below.
- `rs1`: the capability being operated on.
- `rs2`: second operand — new-length value for `CSetBounds`(`Exact`), signed offset delta for `OCA`, **a second Capability Register index (the type-authority capability) for `CSeal`/`CUnseal`**, **the sealed DATA capability for `OCInvoke`** (`rs1` there is the sealed CODE capability), unused for queries. The field is reinterpreted per-`funct7` exactly like `funct3`'s dest-kind role already is elsewhere in this format — not a new idiom. This is also a direct, unmodified match to CHERI-RISC-V's own real `CSeal`/`CUnseal` encoding (verified, CHERI ISA spec pp.226/241): both instructions use the exact bit shape `funct7 | cs2[24:20] | cs1[19:15] | funct3=0x0 | cd[11:7] | opcode`, i.e., Veda-Core's existing Custom-2 R-type layout already matches field-for-field — nothing new needed structurally, only a new interpretation of an existing field.
- `funct3`: destination-register-file selector — `0` = result goes to a GPR (the query ops), `1` = result goes to a Capability Register (`CSetBounds`/`CSetBoundsExact`/`OCA`/`CSeal`/`CUnseal`/`OCInvoke`, though `OCInvoke` shares this same shape without actually reading `rd`, see below).
- `rd`: destination (GPR or capability register, per `funct3`) — **except `OCInvoke`, whose `rd` field is reserved (must encode as `0`) and unused**: real CHERI's own `CInvoke` has no destination-register field either (CHERI ISA spec p.209) — its two outputs, `PCC`/`IDC`, are architecturally fixed, not instruction-selectable, and Veda-Core mirrors this exactly (see below).

**`CSetBounds`/`CSetBoundsExact`** — semantics tightened this pass to match the `Base`/`Length`/`Offset` field fix (Section 2): `cd.Base = cs1.Base + cs1.Offset` (narrows the object window to start at the capability's *current* position, not its original start — direct adaptation of CHERI's real `CSetBounds`, which narrows `base`/`top` around the current `address` the same way, verified CHERI ISA spec p.229), `cd.Length = rs2` (truncated/range-checked against the new 16-bit `Length` field, Section 2), `cd.Offset = 0` (the narrowed capability's cursor resets to its own new start). `CSetBoundsExact` traps instead of rounding if the requested bounds aren't exactly representable; `CSetBounds` rounds. Both clear `cd.Tag` if `cs1` was already sealed (Section 1, "Sealed-capability enforcement," below) or if the requested bounds would exceed `cs1`'s own current window.

**`OCA` (Object Capability Adjust)** — resolved a previous pass by direct adaptation of CHERI-RISC-V's own real `CIncOffset` instruction (verified, CHERI ISA spec p.207: *"Capability register `cd` is set equal to capability register `cs1` with its **address** replaced with `cs1.address + rs2`. If the resulting capability cannot be represented exactly, or if `cs1` was sealed, then `cd.tag` is cleared."*). `OCA` is this same operation adapted to Veda-Core's `Base`/`Length`/`Offset` model (Section 2) instead of CHERI's flat address space: `rd = rs1` with its **`Offset`** field replaced by `rs1.Offset + rs2` (a GPR-held signed delta). If the resulting value would fall outside `[0, rs1.Length)`, **or if `rs1` was already sealed**, `rd.Tag` is cleared rather than trapping — a **soft-fail**, directly matching both CHERI's own `clearTagIf`/`clearTagIfSealed` pattern on `CIncOffset` and Veda-Core's own existing `Bind-NoTrap` precedent in Object-Bind (Section 4). This resolves the gap Custom-1 (Veda-Atomic) depends on: `OCA` is the missing instruction that lets software position a capability register at an exact target offset before issuing an atomic or NMC operation, mirroring how real RISC-V AMO instructions rely on the target address already being computed into `rs1` before the AMO fires. (CHERI additionally defines an immediate-offset variant, `CIncOffsetImm` — deliberately not added to `OCA` in this pass: the register-form alone satisfies the identified need, and adding an immediate form purely for symmetry would be scope creep against the project's own simplicity-first principle. Flagged as a defer-able future addition, not a gap.)

**`CSeal` / `CUnseal`** — resolved this pass by direct adaptation of CHERI-RISC-V's own real `CSeal`/`CUnseal` instructions (verified, CHERI ISA spec pp.226/241-242, full semantics read, not summarized from a fragment). Real CHERI semantics for `CSeal cd, cs1, cs2`: *"Capability register `cd` is replaced with capability register `cs1`, and is sealed with otype equal to the address field of capability register `cs2`. If `cs2` is unable to authorize the sealing, or if `cs1` was already sealed, then the tag field of `cd` is cleared."* — with the authorization condition being `cs2.tag & !isSealed(cs2) & cs2.permit_seal & (cs2.cursor >= cs2.base) & (cs2.cursor < cs2.top) & (cs2.cursor <= max_otype)`. `CUnseal cd, cs1, cs2` is the mirror: unseal `cs1` using `cs2` as authority, requiring `cs2.tag & !isSealed(cs2) & isSealed(cs1) & cs2.permit_unseal & (cs2.cursor == cs1.otype) & (cs2.cursor within cs2's own bounds)`; on failure, `cd.tag` is cleared.

Veda-Core's adaptation, term-for-term:
- CHERI's "address" (a raw pointer into a flat space) becomes Veda-Core's **Offset** (already an existing field, established via `OCA` — Veda-Core has no flat address, only object-relative offsets, so this is the natural substitution, not an approximation).
- CHERI's "cursor within `cs2`'s base/top" becomes "`cs2.Offset` within `cs2`'s own `[0, Length)` window" — **no new structural field needed**: the same `Base`/`Length`/`Offset` triple every Veda-Core capability already carries (Section 2) is simply given a second role when a capability is used as a type-authority operand, exactly mirroring how CHERI reuses its one pointer-bounds mechanism for both ordinary data capabilities and type-authority capabilities rather than inventing a separate "otype-range" structure.
- `otype` (already reserved, 16 bits, Section 2) gets its real semantics now: sealable range `0x0000`–`0xFFFE`; `0xFFFF` (all-ones) is the **UNSEALED** sentinel, directly generalizing CHERI's own "all-ones = unsealed" convention (CHERI: `otype = 2^XLEN − 1`, i.e., all-ones in the implementation's own otype width — verified, CHERI ISA spec p.4150/4170) to Veda-Core's narrower 16-bit field. Object-Bind (Bind/Bind-NoTrap/Rebind, Section 4) always populates a freshly-derived capability's `otype` with `0xFFFF` (unsealed) — sealing only ever happens explicitly via `CSeal`, never implicitly from the ODT. **Only one sentinel is reserved this pass** (not two, unlike CHERI's `2^XLEN−1`/`2^XLEN−2` pair for unsealed/sentry) — the second sentinel exists in CHERI to support sentry capabilities for `CJALR`-style fast control-flow unsealing, which is out of scope here (see Section 6, item 7): reserving it now with no consumer would be speculative, not grounded.
- `Permit_Seal`/`Permit_Unseal` (Section 2, previously-reserved bit positions) are **activated** this pass — a capability can only authorize sealing/unsealing within its own `[0, Length)`-bounded otype range if it carries the matching permission bit, exactly matching CHERI's `cs2_val.permit_seal`/`cs2_val.permit_unseal` checks.
- Both instructions clear `cd.Tag` (soft-fail) on authorization failure, matching CHERI's `clearTagIf` exactly — consistent with the soft-fail convention already established for `OCA` and `Bind-NoTrap`.

**`OCInvoke`** — resolves Section 6's former item 7 (`CInvoke`-equivalent domain transition, deferred since that item was first identified). A term-for-term adaptation of real CHERI's own `CInvoke` (verified, CHERI ISA spec p.209, `7.4 CHERI-RISC-V INSTRUCTIONS: CInvoke`, full semantics/exception-order read directly from source, not summarized from the Chapter 3 architectural overview alone). Real CHERI semantics: `CInvoke cs1, cs2` checks that both operands are valid, sealed, share a matching `otype`, both carry `Permit_Invoke` (CHERI: `permit_cinvoke`), `cs1` carries `Permit_Execute`, and `cs2` does **not** — then atomically unseals both and installs `cs1` into `PCC` (the program-counter capability) and `cs2` into `C31`, the *last* entry in CHERI's own 32-register capability file (a software ABI convention CHERI itself uses, not a separate physical register — confirmed directly from source: `C(31) = unsealCap(cs2_val)` is an ordinary capability-register-file write, index 31, nothing more), with control transferred directly to the resolved target address.

Veda-Core's adaptation, term-for-term:
- `rs1` (`cs1`, the sealed CODE capability) and `rs2` (`cs2`, the sealed DATA capability) are Veda-Core's own existing rs1-capability/rs2-capability fields (Section 1's own already-established shared positions) — no new operand-encoding mechanism.
- **`c15` is the fixed target for the unsealed DATA capability** ("IDC," Invoked Data Capability) — CHERI's own `C31` convention adapted proportionally to Veda-Core's smaller, 16-entry (not 32-entry, not GPR-overlaid) Capability Register File: the *last* entry, index 15. A software ABI convention exactly like CHERI's own, not a hardware-enforced lock — any other instruction can still target `c15` like any ordinary capability register; `OCInvoke` simply always writes there on success, with no destination-register field to redirect it elsewhere (matching CHERI's own identical choice, not a Veda-Core-specific restriction).
- **Scope deviation from real CHERI, partially closed as of Milestone 14** (`veda-core/PCC_COMPARTMENT_DESIGN.md`/`MILESTONE_14_RESULTS.md`): CHERI's own `CInvoke` also installs the unsealed CODE capability into `PCC` — a full capability struct, later inspectable via `CGetPCC`, and consumed by every subsequent instruction fetch for bounds/permission enforcement. Veda-Core still has no full `PCC` struct (`Object_ID`/`Perms`/`otype`/`Reserved` are not tracked for the active compartment), but real, genuine fetch-time enforcement now exists, in both Sail and RTL, for the subset this project found a real consumer for: `OCInvoke`'s own success path narrows two new persistent registers (`veda_pcc_base`/`veda_pcc_length`, both Sail and RTL) to `cs1`'s own `Base`/`Length`, and every subsequent instruction fetch is checked against them — a genuine hard-trap (`cause = 0x01`, reused; `cap_idx = 16`, the "this was PCC" sentinel, mirroring real CHERI's own `PCC_IDX = 0x10`) if execution tries to leave the invoked compartment. `OCInvoke` still extracts the unsealed code capability's own resolved target address (`Base + Offset`, the same real `CGetAddr` semantics already established) and redirects PC to it directly — a real, unconditional hardware jump, achieving CHERI's own real "atomic unseal-and-jump" property literally. `Perms`-on-`PCC` (a real `PCC`-level permission check distinct from the capability-register-level checks `OCInvoke` already performs on its operands before entry) remains genuinely out of scope — no real consumer exists in this project's current instruction set to justify it yet, named explicitly in `PCC_COMPARTMENT_DESIGN.md` §7, not silently dropped.
- Real CHERI check order, mirrored exactly, not re-derived: `Tag(cs1)` → `Tag(cs2)` → `Seal(cs1)` → `Seal(cs2)` → matching `otype` → `Permit_Invoke(cs1)` → `Permit_Invoke(cs2)` → `Permit_Execute(cs1)` must hold → `Permit_Execute(cs2)` must **not** hold. Any failure is a real hard trap (Section 3), reporting whichever specific capability register (`cs1` or `cs2`) actually failed the check — the first genuine consumer of `cause = 0x04` (Type Violation) and `cause = 0x19` (Permit_Invoke Violation), both reserved in Section 3 since this item was first identified, and the first real exercise of `cause = 0x11` (Permit_Execute Violation), reserved earlier but never previously triggered by any instruction.
- `Permit_Execute`/`Permit_Invoke` (Section 2, previously-reserved bit positions 1 and 10) are **activated** this pass.
- CHERI's own trailing `PCC`-relocation/fetch-alignment checks (`have_pcc_relocation`, `min_instruction_bytes`) are still omitted (no `PCC`-relocation/fetch-alignment concept exists in this project); its own `inCapBounds` check, however, is now real — see the `PCC`-bounds paragraph above.

**`OSpecialRW`** — resolves `NEXT_STEPS_ROADMAP.md` §2.5 ("capability-authority-gated `ODT-Populate`/`ODT-Destroy`"). A term-for-term adaptation of real CHERI's own `CSpecialRW` (verified, CHERI ISA spec §4.3.6/p.235, full semantics read, not summarized): reads and writes Veda-Core's own single Special Capability Register, the **ODA** (Object Descriptor Authority) — a real, delegatable capability-authority context, kept outside the 16-entry CRF since it plays a genuinely different role (an authorization context for privileged instructions, not a general-purpose capability register). `funct7 = 0010011`, the next unused Custom-2 slot after `OCInvoke` (`0010010`).

Veda-Core's adaptation, term-for-term:
- Real CHERI's own `CSpecialRW cd, scr, cs1` takes an `scr`-index operand (CHERI has many SCRs: `PCC`, `DDC`, per-mode trap/scratch/exception-PC registers). Veda-Core has exactly one SCR, so `OSpecialRW cd, cs1` needs no such operand — it always targets the ODA.
- Real semantics preserved exactly: `cd` receives the ODA's value from **before** this instruction's own write (a genuine atomic read-then-write, not two independent operations — matters when `cs1 == cd`), then the ODA is overwritten with `cs1`.
- Real CHERI's own "writing/reading the zero register skips that half" optimization does not transfer directly — Veda-Core's Capability Register File has no `c`-zero-register equivalent the way GPRs have `x0` — so `OSpecialRW` always performs both halves. A stated, deliberate simplification, not a silent omission.
- **Gated on ordinary privilege alone** (`cur_privilege == Machine` / RTL's `$priv`) — real CHERI's own SCR-write rule needs `PCC.perms` to grant `Permit_Access_System_Registers`. Veda-Core's own `PCC`-equivalent (Milestone 14, above) now exists and is genuinely enforced, but deliberately tracks only `Base`/`Length`, not `Perms` — `PCC_COMPARTMENT_DESIGN.md` §7 names this precisely: no real consumer for a `PCC`-level permission check exists anywhere in this project's current instruction set, so adding one now would be unused surface area. Using the already-established, already-verified ordinary-privilege convention here remains the honest floor, not an invented shortcut.

**`ODT-Populate`/`ODT-Destroy`'s own authorization (Section 5.1) is now real capability-authority-gated, not privilege-only.** Legal when **either** ordinary privilege holds **or** the ODA holds a live, unsealed capability carrying `Permit_Access_System_Registers` — a real **OR**, not a replacement, matching CHERI's own layered "ring-based privilege coexists with capability control of ring-related privilege" model exactly (verified, Section 3.11.1). `Permit_Access_System_Registers` (Section 2, previously-reserved bit 7, present since CHERI adoption at Milestone V-B) is **activated** this pass — its first real consumer.

**Sealed-capability enforcement — the actual "compartmentalization" half of this gap, not just the seal/unseal instructions themselves.** Verified by reading four independent real CHERI instruction definitions in full (`CSeal`, `CUnseal`, `CSetBounds` at ISA spec p.229, and `CJALR`/`CLoadTags` at pp.209/217): CHERI draws a real, consistent line between two categories, not one uniform rule —
- **"Manipulate" instructions** (derive a new capability value from an existing one: `CIncOffset`/`OCA`, `CSetBounds(Exact)`, `CSeal`, `CUnseal`) — soft-fail, `clearTagIfSealed`, no trap. Already Veda-Core's convention for `OCA`; **this pass additionally applies it to `CSetBounds`/`CSetBoundsExact`** (Section 1, above), which were previously specified without this check — a genuine refinement caught by this research, not present before.
- **"Use" instructions** (actually dereference the object, or transfer control through the capability: `CLoadTags`, `CJALR`) — **hard trap**, `CapEx_SealViolation`, verified directly from both instructions' real semantics (`if isCapSealed(cs1_val) then handle_cheri_reg_exception(CapEx_SealViolation, cs1)`).

Veda-Core adopts the same split. `OCL`/`OCS`/`NMC_ADD` (Custom-0) and Veda-Atomic (Custom-1) all dereference the object their capability-register operand describes — actual object access, not manipulation of the capability's own metadata. **A sealed `rs1` on any of these now traps**, `cause = 0x03` (Seal Violation, already reserved in Section 3, now activated). Object-Bind's `Rebind` mode (Section 4) recomputes a capability register's contents from the ODT — a "manipulate," not a "use" — so a `Rebind` targeting an already-sealed capability register **soft-fails** (`Tag` cleared) rather than trapping, joining the same family as `OCA`/`CSetBounds`. `Bind`/`Bind-NoTrap` are unaffected (they always populate `rd` fresh, `otype = 0xFFFF`, regardless of `rd`'s prior contents — CHERI has no equivalent "was the destination previously sealed" check for its own capability-loads-from-memory either, since sealing is a property of a register's current contents, not a persistent property of the register itself). The Query family (`CGetBase`/`CGetLen`/`CGetPerm`/`CGetTag`/`CGetType`/`CGetAddr`/`CGetOffset`) remains unconditionally allowed on sealed capabilities, unchanged — verified directly from `CGetTag`/`CGetType`'s real semantics (pp.205/207), neither of which examines seal state at all, matching CHERI's own principle that capability *metadata* is always inspectable even when the capability itself is sealed or invalid.

## 2. The CRF Blueprint (Capability Register File)

16 registers (`c0`–`c15`), each 128 bits + 1 out-of-band Tag bit, kept as a register file physically
**separate** from the 32 RVA23 integer GPRs. **Register-count/organization rationale, added retroactively
after a full standards-alignment review** (`CRF_ARCHITECTURE_ALIGNMENT_VERDICT.md`) confirmed this
choice had never actually been evaluated against real CHERI-RISC-V's own convention before being fixed
here — every other number in this section has a cited source; this one did not, until now:

- **Not a literal CHERI-merged file (capability metadata folded into all 32 GPRs), and this is not an
  arbitrary departure**: real CHERI-RISC-V's switch from CHERI-MIPS's own earlier split register file to
  today's merged-only convention was causally enabled by CHERI Concentrate compressing the architectural
  capability to exactly `2×XLEN` (128 bits for RV64) — "with register tags and 128-bit compressed
  capabilities, extending existing general-purpose registers to support capabilities became a feasible
  approach, as register size doubled rather than quadrupled" (CTSRD-CHERI/cheri-specification,
  `chap-rationale.tex`, "Capability Register File" section). Veda-Core's own capability is 128 bits
  **uncompressed** (`Object_ID`(23)+`Base`(32)+`Length`(16)+`Offset`(16)+`Perms`(16)+`otype`(16)+
  `Reserved`(8) = 127+1 pad, this section, below) — a full 32-bit `Base` and 16-bit `Length` carried in
  the clear, not a CHERI-Concentrate-style relative-bounds encoding. Folding this into RVA23's own
  32-entry, 64-bit GPR file would make every GPR ≥128 bits, all the time, with no compression to offset
  the cost — the precondition that made merging cheap for real CHERI does not hold here.
- **Not simply widened to 32 while staying separate, either**: no real CHERI variant (or CHERI-adjacent
  architecture) has ever shipped a "wide (32) but still separate/indirection-based" capability register
  file — CHERI-RISC-V's own spec co-specified merged and split options early on, but "in practice, only
  variants of CHERI-RISC-V using a 'merged' register file were implemented in emulators, soft cores,
  toolchains, and operating systems" (same source, `chap-cheri-riscv.tex`). A 32-entry separate file
  would be a Veda-Core-original point with no standards precedent behind it, at the real cost of widening
  the hard 4-bit `vcapidx` field (`veda_types.sail:24`) across every CRF-referencing instruction.
- **What actually makes 16 sufficient**: Object-Bind is a cheap ODT-lookup-and-cache (Section 4, below),
  not a from-scratch bounds computation the way a real CHERI capability must already be self-contained —
  CHERI needs a large, GPR-sized register pool specifically because re-deriving a capability from a raw
  pointer isn't possible; re-deriving a Veda-Core capability from its `Object_ID` is a single ODT read.
  CRF pressure here is "how many live object-handles am I juggling," not "how many raw pointers am I
  threading through this function" — a smaller, architecturally different kind of pressure than what
  CHERI's 32-per-GPR convention was sized to solve. This argument is not yet backed by a quantitative
  cross-architecture study (see the verdict doc's own "Open risks" section) — treat it as the current,
  best-evidenced structural reason, not a closed question.

Confirmed field layout:

| Field | Width | Notes |
|---|---|---|
| **Tag** | 1 bit, out-of-band | Not counted in the 128. Validity bit — matches CHERI's tagged-memory convention exactly. |
| **Object_ID** | 23 bits | **Widened this pass from 16 bits (65,536 objects) to 23 bits (8,388,608 objects)** — a real, cited fix for a real shortfall identified during rigorous scaling-barrier research (`SCALING_BARRIERS_RESEARCH.md` §3), not a speculative round number. Freed by right-sizing the `Reserved` field's generation-counter slice to CHERI-D's real, empirically-justified 8-bit width (below) — exactly 7 bits freed, exactly 7 bits added here, no other field touched. |
| **Base** | 32 bits | The object's real, absolute location as resolved by the ODT (Section 5.1) — copied in unchanged by Object-Bind. |
| **Length** | 16 bits | **Fixed this pass — was previously a 32-bit `Limit` field, a real gap found while re-verifying the spec before writing any Sail code (below).** The object's size, `0`–`65535`. Renamed from `Limit` to `Length` to match wording already used elsewhere in this same document before this fix (`CSetBounds`'s own `rs2` was already documented as a "new-**length** value," Section 1) — this fix aligns the field table with terminology the rest of the spec already assumed, not the reverse. |
| **Offset** | 16 bits | **New field, added this pass to close a real, previously-undetected gap.** The capability's current object-relative cursor, `0 <= Offset < Length`; the object's *real* location is `Base + Offset`. `OCA` (Section 1) explicitly modifies "`rs1.Offset`" and checks it against "the capability's already-established Base/Limit window" — text that had been in the spec for two prior passes describing a field this table never actually defined. Also directly confirmed by Section 1's own original Custom-2 query list, itself unchanged since before this fix, which already separately named `CGetLen`, `CGetOffset`, *and* `CGetAddr` as three distinct queries — i.e., the instruction set already assumed this three-way split; only this field table hadn't caught up. `CGetOffset` returns `Offset` alone; `CGetAddr` returns `Base + Offset` (the real location); `CGetLen` returns `Length`. |
| **Perms** | 16 bits | 12 bits reused directly from CHERI's verified hardware permission list (Global, Permit_Execute, Permit_Load, Permit_Store, Permit_Load_Capability, Permit_Store_Capability, Permit_Store_Local_Capability, Permit_Access_System_Registers, plus Permit_Seal/Permit_Invoke/Permit_Unseal/Permit_Set_CID) + 1 confirmed Veda-Core-specific addition, `Permit_NMC_Compute` + remaining spare bits. **`Permit_Seal`/`Permit_Unseal` activated a previous pass** (authorize a capability to mint/redeem `otype`s within its own Base/Length-bounded range via `CSeal`/`CUnseal`, Section 1). **`Permit_Invoke` activated a previous pass** — gates `OCInvoke` (Section 1, formerly Section 6 item 7), Veda-Core's own `CInvoke`-equivalent. **`Permit_Access_System_Registers` activated this pass** — gates the ODA's own authorization for `ODT-Populate`/`ODT-Destroy` (Section 1's `OSpecialRW`/`ODT-Populate` writeups, `NEXT_STEPS_ROADMAP.md` §2.5, Milestone 11), the real permission bit CHERI's own SCR-access rule uses, present in this table by name since CHERI adoption but unconsumed until now. `Permit_Set_CID` remains reserved/inactive — tied to CHERI's own `CGetCID`/`CSetCID` compartment-identifier mechanism (microarchitectural side-channel tagging, e.g. branch-predictor entries), a distinct, still-unaddressed item. |
| **otype** | 16 bits | `0xFFFF` (all-ones) = **UNSEALED** sentinel — every capability freshly derived via Object-Bind (`Bind`/`Bind-NoTrap`/`Rebind`) carries this value; generalizes CHERI's own all-ones-in-the-implementation's-otype-width convention (verified, CHERI ISA spec p.4150/4170: `otype = 2^XLEN − 1`, truncated to the implementation's field width) to Veda-Core's 16-bit field. `0x0000`–`0xFFFE` = the sealable range, minted by `CSeal` and redeemed by `CUnseal` (Section 1). Only one sentinel value is reserved — CHERI additionally reserves a second (`2^XLEN−2`) for sentry capabilities, out of scope here since sentries exist to support `CJALR`-style capability-jump unsealing and Veda-Core has no such control-flow mechanism yet (Section 6, item 7). |
| **Reserved/Flags** | 8 bits | **Right-sized this pass from 15 bits to 8**, now used *entirely* by the ODT generation counter (Section 5.1) — no spare bits remain. The 8-bit width is not an arbitrary shrink: it directly matches CHERI-D's real, empirically-derived, hardware-prototyped per-allocation generation-counter width (arXiv 2606.19055, verified in full — see `SCALING_BARRIERS_RESEARCH.md` §3/§6 for the full bit-budget arithmetic and for the honest caveat that CHERI-D's *mechanism* — inline-with-data colocation — does not transfer to Veda-Core's cache-less design, only the *width* is borrowed as a cross-checked starting point pending Veda-Core's own real workload data). Generation is copied in by Object-Bind and re-checked by the MSA on every dereference to detect a stale capability after its `Object_ID` was freed and reallocated. |

Total: 23(Object_ID)+32(Base)+16(Length)+16(Offset)+16(Perms)+16(otype)+8(Reserved) = 127, +1 padding bit = 128, plus the out-of-band Tag. **Why `Length`/`Offset` are 16 bits, not 32**: the pre-fix table (`Base`(32)+`Limit`(32)) had no room left in the fixed 128-bit budget for a genuinely separate `Offset` field once the gap above was found — every other field is already load-bearing (`Perms`/`otype` have defined bit meanings, `Reserved` already has a claimed slice) and could not shrink without breaking something already decided. Splitting the freed 32 bits from the old `Limit` field evenly into `Length`(16)+`Offset`(16) fits the existing budget exactly with zero bits added or removed anywhere else, and 16 bits caps a single object's size at 65,536 — a real, honest trade-off (the pre-fix design's theoretical, if inconsistent, 32-bit `Limit` could describe far larger regions), but a defensible one: the address-less, object-based design philosophy already frames an "object" as a data-structure-sized unit, not a large flat array, and this cap is the same order of magnitude as real historical precedent for a similarly-scoped system (Plessey System 250's own segments capped at 64K 24-bit words, Section 5.1). Growing past this later would need either a wider capability register (cascading into `OCL.C`'s already-fixed 128-bit width, Section 1) or a CHERI-style compressed encoding — flagged honestly as a real, not-yet-needed future constraint, not silently designed around. **Note `Length`/`Offset` deliberately did not grow alongside `Object_ID` this pass** — the two questions (how many objects can exist, how big can one object be) are independent, and this pass's research (`SCALING_BARRIERS_RESEARCH.md` §3) only established a real, cited case for widening the former.

**Confirmed, explicit decision**: the NMC compute-operation selector is **not** stored in the capability register — it lives in the issuing instruction's `funct7` (Custom-0). This keeps the capability as a generic Object Descriptor rather than a fixed, single-purpose compute command, and keeps execution behavior flexible per-access rather than fixed per-object.

## 3. The Trap Model

**Top-level `mcause` = `24`** (`0x18`) — verified against the real RISC-V privileged spec's Table 104: exception codes 24–31 and 48–63 are explicitly "Designated for custom use." ## 4. Object-Bind

**Format**: I-type, under Custom-0, discriminated by `funct3 = 101`.

```
31                    20 19        15 14    12 11      7 6        0
[  imm[11:0] (mode/flags) ][   rs1 (GPR)  ][  funct3=101 ][    rd    ][0001011]
```

- `rs1`: an ordinary GPR holding the `Object_ID` as a runtime integer value — **not** a capability-register reference. Chosen specifically so `Object_ID`'s width is never hardcoded into the instruction encoding (the confirmed 23-bit field fits easily inside a GPR, and the design isn't constrained if it needs to grow further later — this instruction's own encoding needed zero changes when `Object_ID` was widened from 16 to 23 bits this pass, direct payoff of that original decision).
- `imm[11:0]`: bind-mode field (only 2 bits currently used, 10 reserved):
  - `00` — **Bind**: normal bind; traps (`cause = 0x05`) if `Object_ID` has no valid ODT entry.
  - `01` — **Bind-NoTrap**: clears the destination's Tag bit instead of trapping on a missing object — directly modeled on `[C]LC`'s own verified default behavior for several of its failure conditions (CHERI's primary capability-load instruction silently clears the tag rather than trapping, in the common case).
  - `10` — **Rebind**: refreshes an already-bound capability register's `Base`/`Length`/`Perms`/`otype`/generation from the ODT, **leaving `Offset` unchanged** — this is the concrete mechanism that makes the very first design goal ("the MSA can silently relocate an object without the CPU knowing") actually real: if the object moved, `Base` updates to the new real location but the software's own relative position within the object (`Offset`) is preserved unchanged, exactly the property that makes relocation transparent. Without Rebind, that goal had no instruction to implement it. **Resolved this pass**: `Rebind` targeting a currently-*sealed* capability register (Section 1) soft-fails — `rd.Tag` cleared, ODT refresh skipped — rather than silently overwriting a sealed capability's metadata. This joins the "manipulate" family (`OCA`/`CSetBounds`(`Exact`)/`CSeal`/`CUnseal`) rather than the "use" family, since `Rebind` recomputes register contents rather than dereferencing the object itself — it does not trap.
  - `11` — reserved.
- `rd`: destination Capability Register (`c0`–`c15`).

**Semantics**: ODT lookup by `Object_ID`; on success (`Bind`/`Bind-NoTrap`), populate `rd`'s `Tag`/`Base`/`Length`/`Perms`/`otype` fields from the ODT entry, set `rd.Offset = 0` (a fresh bind starts at the object's beginning; `otype` always set to `0xFFFF`, UNSEALED — sealing only ever happens explicitly via `CSeal`, Section 1), and copy the ODT entry's current generation counter into `rd`'s `Reserved/Flags` field (Section 5.1 — lets the MSA detect, at actual dereference time, whether this `Object_ID` has since been freed and reallocated to a different object). **Milestone 12 addition**: success also *claims* the ODT entry's own `owner_hart` field for the current hart (Section 4.1) — a real side effect on the ODT itself, not just on `rd`, the first time any Object-Bind mode has ever written back to the table it reads from. `Rebind` differs only in leaving `rd.Offset` unchanged, as above. On failure, behavior depends on bind mode (trap vs. tag-clear) as above — now including a real, distinct failure reason, a live object owned by a different hart (Section 4.1).

### 4.1 Concurrent-access policy: exclusive-by-default binding, now hardware-enforced

**Originally added as a policy decision, not new hardware** (`SCALING_BARRIERS_RESEARCH.md` §4), as the real, precedented answer to the multi-core Veda-Atomic/`NMC_ADD` contention shortfall identified during scaling-barrier research. **Milestone 12 makes it real, hardware-enforced logic** — the exact gap this section itself named and deferred ("an owner-hart field in the ODT entry, checked at Bind/Rebind time... real, identified future work").

**Policy, unchanged**: an `Object_ID` is bound by one hart's capability register at a time. Software is expected to treat concurrent Object-Bind of the *same* `Object_ID` from multiple harts as the deliberate, explicit, comparatively rare case — not the default assumption every Veda-Atomic/`NMC_ADD` access has to be designed to survive cheaply.

**Why this is a real answer, not an assumption of convenience**: verified directly against the only publicly-available, commercially-shipping real-world processing-in-memory hardware — UPMEM's DPU system (Gómez-Luna et al. 2022, read in full). UPMEM's DPUs have *no direct inter-DPU communication channel at all*, and their own official Programming Recommendation #2 is *"split the workload into independent data blocks, which the DPUs operate on independently."* Real result: the 13 of 16 real benchmarks *not* needing cross-DPU synchronization see the real hardware beat a modern CPU by 93.0x average; the ones that do need it pay a large, explicitly-documented penalty. Object-Bind already gives software an explicit, visible unit (the bind operation itself) to declare ownership through — this policy just states, in the spec, what UPMEM's shipped hardware discovered was the difference between a workload that scales and one that doesn't.

**The real enforcement mechanism**: the ODT entry (Section 5.1) gains an `owner_hart` field (8 bits — a real, bounded, honestly-scoped design choice, the same reasoning already applied to the ODT's own generation-counter width, `SCALING_BARRIERS_RESEARCH.md` §3/6 — 256 harts is a generous real ceiling for this design's own target scale, not a claim of matching `mhartid`'s full `XLEN` width). `VEDA_OWNER_UNOWNED` (all-ones, `0xFF`) is the sentinel: a freshly populated (or destroyed-and-repopulated) object belongs to no hart until claimed. `Bind`/`Rebind` check `entry.owner_hart == VEDA_OWNER_UNOWNED | entry.owner_hart == mhartid` — the real, already-existing `mhartid` architectural register, not a new one invented for this purpose. If the entry is unowned or already owned by the calling hart, the bind (or re-bind, idempotently) succeeds and the ODT entry's own `owner_hart` is (re-)claimed for `mhartid` — a real write-back into the table `Bind` itself reads from, the first time any Object-Bind mode has done this. If the entry is live but owned by a genuinely *different* hart, that is now a real, distinct authorization failure: plain `Bind` hard-traps (`cause = 0x06`, the first real consumer of this previously-reserved slot); `Bind-NoTrap` soft-fails, matching its own established convention for every other failure reason; `Rebind` also soft-fails — it never traps for *any* reason, owner mismatch included, the same "manipulate, not use" principle already governing its sealed-destination check (above).

**What this still does not claim**: it does not forbid sharing — a hart that already owns an object can still choose to hand a bound capability to another hart through ordinary means (shared memory, a message), the policy only governs who can *originate* a fresh `Object-Bind` against a still-live entry. **`ODT-Destroy` is deliberately, permanently NOT owner-gated** (Section 5.1's own authorization stays privilege/ODA-based, Section 1's `OSpecialRW`) — this was researched, not merely deferred: real CHERI's own architectural precedent for object-capability revocation (CHERI ISA spec §2.3.16, "Revocation of sealed capabilities" — the exact real-world source `SCALING_BARRIERS_RESEARCH.md`'s own ODT generation-counter design was already modeled on) places revocation authority with *"a trustworthy software handler"* / *"a trusted userspace supervisor,"* entirely independent of which capabilities currently reference the object being revoked — the opposite of an ownership-based gate. CHERI's own delegation-tree revocation design (Appendix C.4) reinforces the same principle from a different angle: revocation authority tracks the *delegator*, not the current holder. `Bind`'s own owner-hart policy and `ODT-Destroy`'s own privilege/ODA policy are therefore correctly two distinct authority models, not one gap the other should inherit — `Bind`-ownership answers "who may currently use this live object," `ODT-Destroy`'s authorization answers "who may administer this object's lifecycle at all," and conflating them would be a real, CHERI-inconsistent design mistake, not a natural extension. **This logic is verified against direct ODT-state injection (a test-scaffold precondition, mirroring this project's own established `veda_test_seed_odt()` pattern), not genuine concurrent multi-hart execution** — neither this project's own single-process Sail simulator invocation nor its current single-core RTL can produce two real, concurrently-executing harts; that remains real, distinct, larger future work (`NEXT_STEPS_ROADMAP.md` §2.7).

## 5. The MSA Interface

Explicitly simplified per the direct instruction to keep the MSA to "takes a request, processes it, gives the result" — this replaces the earlier 3-phase Request/Grant/Release handshake and the Integrity Manager (Object Tracking Table + Violation Log), both removed for the reasons below, not merely trimmed for their own sake.

**Why Grant could be removed, not just simplified**: bounds and permission checks now happen entirely at the CPU (Section 3), using capability-register fields already resolved locally. By the time a request reaches the MSA, it has already been validated — there is nothing left for a Grant phase to decide.

**Request (CPU → MSA)**: `{ command, Object_ID, validated_offset, width/data }`

**Result (MSA → CPU)**: `{ data / old-value, done }`

No separate acknowledgment step, no ownership bit, no per-object lock tracking.

**How the CPU waits**: a pipeline stall, not a scoreboard or out-of-order mechanism — the standard, textbook way a simple in-order pipeline handles any multi-cycle operation (the same class of design as the CHERI-extended `Piccolo`/`Flute` cores surveyed during research for this design). The instruction occupies its pipeline stage until the MSA's `done` signal returns; subsequent issue is held up until then.

**Explicitly deferred, not solved**: the Integrity Manager's Object Tracking Table and Violation Log — these only matter once there's a second hart to race against, and this design has none yet. Also explicitly unaddressed: how the MSA hides DRAM data-fetch latency for the object's actual payload once real hardware exists — this was flagged directly during the design discussion as a real, open problem distinct from (and larger than) the metadata-lookup latency problem that Object-Bind's local-caching approach solves. The reframed goal (security/energy-efficiency over raw throughput, explicitly not competing with high-concurrency systems) makes this more tractable but does not make it disappear — it has not been designed yet.

### 5.1 The Object Descriptor Table (ODT)

**Resolved this pass.** Object-Bind (Section 4) has always referred to "an ODT lookup by `Object_ID`," but no prior pass actually designed the ODT's own structure — this closes that gap, since it's the one part of the design with no direct CHERI precedent (CHERI capabilities describe a flat address space directly; there is no `Object_ID → Base/Length` indirection to design in the first place). Researched against six real historical capability systems and one modern microkernel, **each source read in full** (not excerpted to "the relevant section" — a first pass at this research made that mistake and was corrected): the seL4 Reference Manual (v15.0.0, all of Ch.1-9, ~70 pages), and five full chapters of Levy's *Capability-Based Computer Systems* (1984) — Ch.4 Plessey System 250, Ch.5 Cambridge CAP, Ch.8 IBM System/38, Ch.9 Intel iAPX 432, and Ch.10 "Issues in Capability-Based Architectures" (the book's own cross-system synthesis).

- **seL4's CSpace/CNode**: capability addresses are plain integers ("a capability address is simply an integer... [but it] refers to a capability slot"), resolved via a *guarded, multi-level* table walk. Real, well-documented, genuinely the closest precedent for "index into a table, not a raw pointer." But the lookup happens in **kernel software** on an explicit syscall trap — seL4 has no hardware capability-table walker.
- **seL4's VSpace** (read in full as the remaining real precedent for a genuinely *hardware*-walked table, not just seL4's software-walked CSpace): real ISA-native multi-level page tables (RISC-V Sv39-style, x86 PML4, ARM) — confirms multi-level, hardware-walked tables are a real, standard, mainstream technique, not hypothetical. Weighed against this and rejected below, not overlooked.
- **IBM System/38**: not structurally useful (objects self-locate via a segment ID embedded in a 64-bit pointer, no separate table — not applicable, Veda-Core has no flat address space for a segment ID to live in), but the source states a real security lesson directly: *"Because the address space is so large... segment IDs are never reused... The system need not search for dangling references when an object is deleted."*
- **The Cambridge CAP Computer**: the direct structural template. CAP's CPU contains *"a 64-entry capability unit that holds evaluated capabilities... registers implicitly loaded by the microprogram"* from a backing **Process Resource List (PRL)** — exactly Veda-Core's Capability-Register-File-populated-by-Object-Bind-from-the-ODT relationship. The source explicitly contrasts two real alternatives: *"In contrast to the Plessey and CAL-TSS designs, in which capabilities refer to entries in a **system-wide table**, capabilities on CAP refer to entries in a **process-local table**."* **Reading the full chapter (not just this passage) surfaced something the first pass missed**: CAP's own designers wrote a real self-critique (§5.12, "Discussion") — *"Because all capabilities address the PRL, a process-local structure, they cannot be passed easily between processes"* and, in their own words, *"Following their initial experience, CAP's designers felt that the process tree had been much overemphasized in the design. The generality of a multi-level process structure... led to performance and implementation difficulties."* A real, first-party regret about exactly the design axis (process-local hierarchy) this decision rejects — not a hypothetical downside I inferred, but one the original designers lived through and wrote down. The same chapter gives a real, quantified cost of deep indirection: *"A memory reference in a level-2 user process requires four overhead references before the word is accessed, because two capabilities and two PRL entries must be read."*
- **The Plessey System 250** (read in full — the system CAP's own text named as the real-world contrast, not taken on faith): confirms the system-wide table alternative is real and shipped, not just a name-check in someone else's book. Plessey's **System Capability Table (SCT)** is exactly a flat, system-wide, `Object_ID`-indexed table (a 16-bit index — the same width Veda-Core's own `Object_ID` originally shipped at, before this pass's widening to 23 bits, Section 2), holding base/limit per entry — *"the mapping table for 64K descriptors occupies about 589K bytes of storage."* This is a real, shipped commercial data point for a flat table at what was Veda-Core's original ID width, not a hypothetical sizing estimate. Plessey's own retrospective (§4.10) credits its narrow product scope for whatever success it had: *"The targeting of the product to a limited role probably provided the key to any success the System 250 has had — its simplicity."*
- **Ch.10 "Issues in Capability-Based Architectures"** (the book's own synthesis, read in full): the single most load-bearing source for this decision, and the one a first pass at this research skipped entirely. Directly informs, and in one place *corrects*, the analysis below.

**Decision**: the ODT is a **flat, single-level, system-wide table**, indexed directly by the (now 23-bit, widened this pass — see Section 2) `Object_ID` — CAP's PRL structure, Plessey/CAL-TSS's system-wide scope. Reasoning:
- **Flat over multi-level** (rejecting both seL4's guarded-CNode-graph and real hardware page-table-style multi-level walking, having read both as genuine alternatives, not strawmen): Section 5's MSA request/result model is a single, fixed-shape transaction, not a variable-depth walk — a multi-level table would make `Object-Bind`'s latency depend on how deep a given `Object_ID` sits. Ch.10 §10.4 notes real systems solved the *storage* problem this raises differently — Intel 432 went two-level specifically because its ID space (24 bits, 16M objects) was too large to keep resident.
- **Honest update, this pass, now that `Object_ID` is 23 bits (8.4M objects) rather than 16 (64K)**: the original reasoning here leaned on "Veda-Core's ID space is the same order of magnitude as Plessey's" — that is no longer true; at 8.4M objects, Veda-Core's ID space is now much closer to Intel 432's 16M than to Plessey's 64K, the exact scale Intel 432's own designers found too large to keep flat. This is flagged rather than silently left as stale supporting evidence. **The flat decision still holds, but now for the reason that was always the real, load-bearing one and doesn't depend on ID-space size**: Intel 432's constraint was keeping the table *resident in fast, on-chip storage* — a hardware-cost concern specific to early-1980s silicon. Veda-Core's ODT was already decided, independent of `Object_ID` width, to be **ordinary DRAM-resident memory, not on-chip SRAM** (below) — the specific resource Intel 432 ran out of was never a resource Veda-Core's ODT depended on at any width. Choosing flat at 8.4M entries is not ignoring the problem Intel 432 solved with two levels; it's recognizing Veda-Core never had that problem in the first place, because it never asked the table to fit somewhere small.
- **System-wide over per-process**: CAP's own designers' documented regret (above) about overemphasizing per-process hierarchy is direct, first-party evidence against building it here, not just an absence of present need. Veda-Core also has no process/privilege hierarchy yet to hang per-process indirection on (Section 6: no general M/S/U-mode architecture, single-hart only).
- **Memory-resident, not on-chip SRAM**: Plessey's real, shipped 589KB SCT confirmed a flat table was a proven, non-hypothetical design point at the original 16-bit ID width. **Honest real arithmetic at the new 23-bit width** (per-entry: `valid`(1 bit)+`Base`(32)+`Length`(16)+`Perms`(16)+`generation`(8, Section 2) = 73 bits, ~10 bytes with realistic byte-alignment): 8,388,608 entries × ~10 bytes ≈ **80-100 MiB**, roughly 128x Plessey's real 589KB (exactly 2^7, tracking the 7 bits `Object_ID` grew by). This is a real, substantial jump in absolute size, stated plainly rather than glossed over — but it does not change the design decision, because the ODT was never asked to fit in scarce on-chip SRAM at *either* width. It lives in ordinary DRAM, walked fresh by the MSA on every `Object-Bind` with no caching layer — matching Veda-Core's own "cache-less" pillar — and 80-100 MiB is an unremarkable footprint for real, modern DRAM capacity, unlike the resource-constrained hardware Plessey (1970s-80s) and Intel 432 (early 1980s) actually shipped into.

**A real security gap, and an honest account of what actually solves it.** System/38's "IDs never reused" lesson doesn't transfer: even at the now-widened 23-bit `Object_ID` (8.4M values), permanent non-reuse is still impractical for a system creating and destroying objects continuously (System/38's had a much larger, effectively-never-exhausted address space to make that lesson free; Veda-Core's isn't, at either the original 16-bit or the new 23-bit width). Ch.10 §10.4, read in full, states the dangling-reference problem precisely and names the *only two* solutions the historical systems it surveys actually used: *"(1) an object cannot be deleted (or its descriptor reallocated) while capabilities exist for the object, or (2) all capabilities for an object to be deleted must be found and disabled."* Plessey's real mechanism is option (1) — SCT entries are not reallocated while active capabilities reference them, enforced by a background garbage-collector process. **Neither of the two documented solutions is a generation counter.** The fix proposed here — each ODT entry carries a generation counter, copied into the capability's `Reserved/Flags` bits (Section 2) at bind time and re-checked by the MSA on every dereference, mismatch → Tag Violation — is **my own synthesis**, informed by the problem these sources document precisely but not literally attested in any of them. Said plainly, not overclaimed: this is a third option neither Plessey nor Intel 432 used, reasoned from their stated problem, not copied from a named historical solution.

**Correcting an overclaim from the first pass at this research**: that pass stated the generation counter gives Veda-Core "real revocation... without a derivation tree." Having now read Ch.10 §10.9 ("Revocation") in full, that overstates what the mechanism does. The book's own definition of revocation is *selective* — retracting one holder's access while another holder's capability for the *same still-live object* stays valid — and its own survey is sobering: *"With the exception of the System/38, none of the systems examined have attempted to support revocation"* (System/38's real mechanism costs a process-local profile-table lookup on every unauthorized-pointer use). Veda-Core's generation counter does **not** provide that: it detects a *stale* capability after its `Object_ID` was freed and reallocated to a *different* object — a real, valuable safety property, but narrower than selective revocation, and it revokes *all* outstanding capabilities for a destroyed object uniformly, not one holder at a time. True selective revocation, if ever needed, would require something closer to System/38's per-holder authority table or a CHERI/seL4-style derivation tree — deliberately out of scope here, and now stated as such rather than folded into an overclaimed "solved."

**ODT population — resolves the item flagged open in `FORMAL_VERIFICATION_PLAN.md` §3, encoding decided this pass (Milestone V-B).**

**Data model** (unchanged from the earlier pass): `ODT-Populate` writes `Base`/`Length`/`Perms` for a given `Object_ID`; `ODT-Destroy` invalidates an entry and bumps its `generation` counter so any capability still holding the old generation fails the re-check added in Milestone V-B (above) rather than silently aliasing a future occupant of the same `Object_ID`.

**Format, real and concrete**: R-type, Custom-0 (same opcode as `OCL`/`OCS`/`NMC_ADD` — a natural sibling, since Object-Bind's own I-type variant already lives under this same opcode as "capability binding," and ODT-Populate/Destroy is "the thing Object-Bind reads from"), `funct7 = 0000011`, discriminated from `ODT-Destroy` by `funct3` (`000` = Populate, `001` = Destroy — reusing `funct3` as a small mode selector under one `funct7`, exactly how Custom-2's `funct3` already means different things per `funct7` value, not a new idiom). `rs1` = a GPR holding `Object_ID` (mirrors Object-Bind's own `rs1` convention field-for-field). `rs2` = a GPR holding a packed descriptor word for Populate — `Base[31:0]` in bits `[63:32]`, `Length[15:0]` in bits `[31:16]`, `Perms[15:0]` in bits `[15:0]`, exactly 64 bits, fitting one GPR precisely with zero waste; unused/ignored for Destroy. `rd` unused (written `0` on success).

**Authorization — real capability-authority gating now exists, layered on top of ordinary privilege, not replacing it.** R-type's two source-operand slots are already fully committed to `Object_ID` and the packed descriptor — there is no operand slot left for a capability-authority operand directly on `ODT-Populate`/`ODT-Destroy` themselves without exceeding what one 32-bit instruction can encode. The real fix (Milestone 11, `rtl/MILESTONE_11_RESULTS.md`): a capability-authority operand doesn't need to live on these two instructions at all — it lives in the **ODA** (Object Descriptor Authority), Veda-Core's own single Special Capability Register, term-for-term adapted from real CHERI's own SCR model (CHERI ISA spec §4.3.6). Software delegates authority into the ODA via `OSpecialRW` (Section 1's own new "OSpecialRW" entry, Custom-2 `funct7 = 0010011`) — itself gated on ordinary privilege alone, since a capability-gated version would need `PCC.perms` checking, and Veda-Core's own `PCC`-equivalent (Milestone 14, Section 1) deliberately tracks only `Base`/`Length`, not `Perms` (no real consumer for a `PCC`-level permission check exists yet, `PCC_COMPARTMENT_DESIGN.md` §7) — and `ODT-Populate`/`ODT-Destroy` are now legal when **either** `cur_privilege == Machine` **or** the ODA holds a live, unsealed capability carrying `Permit_Access_System_Registers` (bit 7, already present in the Perms table since CHERI adoption at Milestone V-B, never consumed by any real instruction until now). This is a real **OR**, not a replacement — ordinary M-mode privilege still always suffices on its own, unchanged since Milestone 4, matching CHERI's own layered model exactly (verified, Section 3.11.1: "ring-based privilege" and "capability control of ring-related privilege" coexist in real CHERI, one doesn't replace the other).

#### A real failure, examined for what it teaches: the Intel iAPX 432

Read Levy's Ch.9 (iAPX 432, in full) and Colwell, Gehringer & Jensen's 1988 ACM TOCS paper *"Performance Effects of Architectural Complexity in the Intel 432"* (the definitive external post-mortem, since Levy's 1984 book predates it and only notes, correctly but without the later quantification, that *"it is fair to say that the Intel 432 has not been a commercial success"* and had real *"performance problems"*). This is the clearest documented capability-architecture *failure*, and it teaches concrete, load-bearing lessons for Veda-Core's own design, not just a cautionary anecdote:

- **Every operand, not just memory accesses, paid object-indirection cost.** iAPX 432 had no general registers separate from the object system — even a simple scalar operand reference went through an access-descriptor lookup. Levy's own numbers: *"four memory references... before the word is accessed"* per operand in the common case, and a `CALL` instruction that cost **300 microseconds on early prototypes**, reduced to *"under 100 microseconds"* only after significant architectural rework (preallocated context objects, local-stack storage resources). **This directly validates a structural choice Veda-Core already made, now with a concrete negative counter-example to point to**: ordinary RV64I arithmetic on GPRs pays *zero* object-model cost in Veda-Core's design — only the explicit `OCL`/`OCS`/`NMC_ADD`/Veda-Atomic instructions touch the capability/object system at all. iAPX 432 made object-indirection ambient; Veda-Core makes it opt-in per instruction.
- **Bit-granular, variable-length instruction encoding** (Levy, §9.7: instructions from *"10 to more than 300 bits"*, decoded via a multi-field `class`/`format`/`references`/`opcode` structure with no fixed alignment) was a major implementation-complexity driver, per Colwell's own analysis. This is a direct negative counter-example validating this spec's existing "Cross-cutting design principle" (Section, below) of keeping every Veda-Core instruction family in fixed 32-bit RISC-V R-type/I-type shapes — not just good taste, but the documented alternative to a real, hard-to-implement design (see "Cross-cutting design principle" at the end of this document).
- **A "no special privileges, everything is uniformly an object" purity had a real cost.** iAPX 432's own discussion (§9.8) states plainly: *"There are no special privileges in the Intel 432 system... mechanisms used by programmer-defined type managers are identical to those used by operating system type managers."* Elegant, and part of why the deep per-operand indirection above was unavoidable *everywhere*, with no fast path. Veda-Core's hybrid architecture — ordinary RV64I as the base ISA, with the object-capability layer added as explicitly-invoked Custom-0/1/2 opcodes rather than replacing the base ISA's addressing model entirely — is a deliberate, now-better-justified choice to keep a fast, ordinary path available and make the capability system opt-in rather than ambient.
- **Colwell's post-mortem attributes a large share of the real-world slowdown to compiler/toolchain immaturity** (25-35% of throughput lost to poor Ada code generation), not architecture alone — even sound hardware can fail commercially if the surrounding toolchain isn't equally mature. A direct, practical caution for this project's own current stage: the formal verification model (`FORMAL_VERIFICATION_PLAN.md`) and eventual RTL both need real maturity before any performance or practicality claim about Veda-Core is made, not just a sound spec.
- **The failure was not purely technical.** Levy's own 1984 assessment: *"The commercial problems of the Intel 432 are probably due in part to premature (and somewhat overzealous) marketing of the product before its implementation and software were ready."* A process lesson, not an architectural one — worth carrying forward as this project's own work moves from spec to RTL.

## Cross-cutting design principle, worth stating explicitly

Every instruction family in this design — OCL's R-type operations, Veda-Atomic, Veda-Cap, and even Object-Bind's I-type variant — keeps register-operand fields (`rs1`, `rs2`, `rd`) at consistent bit positions, and uses `funct3` as the sole discriminator between R-type and I-type interpretations where both exist under one opcode. This was noted repeatedly during design as a genuine, deliberate strength: decode logic built for one instruction family transfers almost unchanged to the others, rather than each custom opcode inventing its own unrelated layout. This isn't just a preference: Intel's iAPX 432 (Section 5.1) shipped bit-granular, variable-length instructions (10 to 300+ bits, no fixed alignment) and paid for it in documented implementation complexity — a real system that took the opposite choice and a real cost that resulted.
