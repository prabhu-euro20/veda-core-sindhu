# Veda-Core PCC-Equivalent Design — Bounding Execution Inside an `OCInvoke`-Entered Compartment

**Status**: Design-stage. No Sail or RTL code written yet. This is the design pass `NEXT_STEPS_ROADMAP.md`'s own Tier 3 item 5 and every one of `MILESTONE_10_RESULTS.md`/`MILESTONE_11_RESULTS.md`/`MILESTONE_12_RESULTS.md`/`MILESTONE_13_RESULTS.md`'s own "Not yet built" sections have named as *"a real `PCC` register with fetch-time capability enforcement"* — read here in the terms real CHERI actually uses it, not assumed from the name alone. The conclusion below is narrower, and differently scoped, than that four-milestone-old phrasing implied; the reasoning for the rescoping is the main content of this document.

---

## 1. The question this document actually answers

Every prior mention of "PCC" in this project's own docs treated it as a single, generically-named missing feature. Before designing anything, the real question needed answering first: **does Veda-Core need a full, ISA-wide, fetch-time-checked PCC the way real CHERI has one, or does it need something narrower?** Read CHERI ISA spec §2.3.12 ("Hybridization with Integer Pointers"), §3.4.6 (SCR definitions), and §11.1.2 ("Program Counter Capability (PCC)," microarchitecture chapter) in full to answer this, not assumed from the name.

## 2. Finding: real CHERI's PCC exists because pure-capability CHERI makes *all* instruction fetch capability-checked. Veda-Core never made that choice.

CHERI ISA spec §2.3.12, verified directly: *"Program Counter Capability (PCC) extends the conventional program counter with capability metadata, constraining instruction fetches."* This exists because CHERI's own pure-capability mode routes **every** memory reference — instruction fetch included — through a capability. PCC is simply "the capability currently authorizing code fetch," and it is *load-bearing for ordinary, unprivileged code the entire time the processor runs*, not just inside some special mode.

Veda-Core made a different, load-bearing, already-stated architectural choice from the very first line of its own spec: *"Veda-Core sits on top of the RVA23 incremental base core... a set of custom, non-standard extensions... layered onto the same underlying hart"* (`VEDA_CORE_SPEC.md`'s own opening). The base ISA's ordinary instruction fetch (`$pc` into `elfmem`) was never redesigned to be capability-addressed — only a new, parallel, **opt-in** data-access mechanism (`OCL`/`OCS`/`OCA`/etc., all reached only by first executing `Object-Bind`) is capability-checked. This is not an oversight; it is the entire reason Veda-Core can exist as a pure RISC-V *extension* rather than a competing, incompatible base ISA.

**Conclusion**: a full, universal, always-active PCC that constrains *all* code all the time — mirroring real CHERI's pure-capability mode exactly — does not fit Veda-Core's own hybrid design and was never actually needed by anything built so far. Building it anyway would be scope invented from the feature's name, not from a real gap in this project's own architecture. This narrows, rather than confirms, the four-milestone-old "Not yet built" phrasing.

## 3. The real, narrower gap: `OCInvoke`'s own compartmentalization guarantee is currently incomplete

Real CHERI's `CInvoke` (CHERI ISA spec p.209, already the basis for `MILESTONE_10_RESULTS.md`'s own `OCInvoke` design) atomically swaps in **two** capabilities on a successful invocation: a data capability into `IDC`, and — the part Veda-Core's own Milestone 10 explicitly, deliberately did not replicate — a code capability that *becomes the new PCC*, from that point on bounding every subsequent instruction fetch to the invoked compartment's own `Base`/`Length`. This is the actual security property `CInvoke` exists to provide: a callee cannot execute (or return control to a caller via anything other than a real, symmetric re-invocation) outside the code region it was specifically handed authority over.

Veda-Core's own `OCInvoke` (`veda_cap_insts.sail`'s `VEDA_OCINVOKE`, `veda_core.tlv`'s `$is_veda_ocinvoke` path) currently redirects `$pc`/`PC` directly to the target address and stops there — nothing constrains where execution goes *afterward*. This is a real, meaningful, currently-open gap in `OCInvoke`'s own compartmentalization claim, not a cosmetic omission: right now, invoked code can jump anywhere, including straight back out of its own compartment, with nothing to stop it. **This — not a generic, universal fetch-time PCC — is the actual, well-scoped feature this project still needs.**

## 4. Real CHERI precedent for exception handling while inside a bounded PCC

Two more real CHERI mechanisms are directly load-bearing for this design, both verified from the spec text rather than assumed:

- **Exception Code Capability** (§3.4.7): *"When an exception is taken, PCC must be replaced with a code capability containing a suitable execution and security context for the exception handler."* — i.e., a trap **must** escape whatever PCC bounds were active, landing in trusted global code. This is the real answer to "what happens if an `OCL`/`OCS` violation fires while inside a narrow, `OCInvoke`-entered compartment" — the trap handler is *expected* to run outside the compartment's own bounds, not be blocked by them.
- **Exception Program Counter Capability** (§3.4.7): *"conventional architectures save the PC following an exception and restore the PC on exception return... CHERI architectures must save and restore the full PCC when handling exceptions."* — the direct, real precedent for a new `mepcc`-equivalent, saved on trap entry and restored on `MRET`, the exact same real pattern Milestone 9's own `$mepc` already established for the plain integer PC.

## 5. Real CHERI precedent for how a PCC bounds violation is actually reported

Checked directly against the Sail pseudocode excerpted in the spec's own instruction-reference listings (e.g. `CJAL`'s own semantics, p. ~460s of the extracted text): a PCC bounds violation is **not** a distinct cause code in real CHERI. It reuses the *same* `CapEx_LengthViolation` cause every ordinary capability bounds check already uses, with `handle_cheri_pcc_exception` — described explicitly as *"as `handle_cheri_cap_exception` except that the capability register number uses the special value `0x10` indicating the PCC register"* — the only difference being a **sentinel register-index value** (`0x10` = 16) that can never collide with a real capability register (CHERI's own real register file only goes up to 31, decimal, with 0-15 sometimes reserved by convention and 16 chosen as clearly outside the "ordinary GPCR you'd actually name here" range for this purpose).

This maps unusually cleanly onto a real, **already-present, currently-unused** bit of headroom in Veda-Core's own `xtval` encoding: `VEDA_CORE_SPEC.md` §3 already documents `cap_idx` as a 5-bit field in the layout diagram, while every real Sail (`veda_xtval(cap_idx : bits(4), ...)`, zero-extended to 5 bits) and RTL (`$veda_trap_cap_idx[3:0]`) call site today only ever produces a 4-bit value (0-15, one of the 16 real capability registers) — the top bit has been reserved, unused headroom since Milestone 9, not a new field this design needs to invent. **Decision**: mirror CHERI's own exact choice — a PCC bounds violation reuses `cause = 0x01` (Bounds/Length Violation, already active, no new cause code needed at all — a stronger, more faithful, more minimal answer than this project's own earlier-assumed "new cause code" premise), with `cap_idx = 5'b10000` (16 decimal) as the "this was PCC, not a real capability register" sentinel — the exact same numeric value real CHERI uses for the same purpose, not independently chosen.

This does require one real, honest implementation cost that must be named up front: every current Sail/RTL call site that builds a trap's `cap_idx` argument is typed/wired for a **4-bit**, always-real capability-register index (Sail's `vcapidx`; RTL's `$veda_trap_cap_idx[3:0]`) — none of them can express the sentinel today. Widening this to genuinely carry a 5-bit value (real index 0-15, or sentinel 16) is real, if small, plumbing work, not a free consequence of the layout already having room for it on paper.

## 5a. Real Sail extension hooks verified directly from the checked-out source, not assumed

Before designing the mechanism further, the actual, concrete Sail hooks were read directly (`toolchain/sail-riscv/model/postlude/fetch.sail`, `model/core/addr_checks.sail`, `model/postlude/step.sail`, `model/core/callbacks.sail`, `model/core/csr_begin.sail`, `model/extensions/I/base_insts.sail`, `model/exceptions/sys_exceptions.sail`):

- **`ext_fetch_check_pc(start_pc, pc) -> option(ext_fetch_addr_error)`** (default in `core/addr_checks.sail`, `type ext_fetch_addr_error = unit`) is called by `fetch()` **before every instruction fetch** and is exactly the real, purpose-built extension point for a fetch-time bounds check — confirmed by reading `fetch()`'s own body, which calls it first, before alignment/RVC/memory-protection checks. A `Some(e)` return becomes `F_Ext_Error(e)` → `Step_Ext_Fetch_Failure(e)`.
- **`ext_handle_fetch_check_error(e : ext_fetch_addr_error) -> unit`** is the real handler Sail dispatches `Step_Ext_Fetch_Failure` to (`step.sail`, `Step_Ext_Fetch_Failure(e) => ext_handle_fetch_check_error(e)`) — this function must itself perform the real, state-mutating trap delivery. Confirmed the real mechanism for this is `handle_exception(xtval, exceptionType) -> unit`, the same function ordinary base-ISA fetch failures use (`step.sail`: `Step_Fetch_Failure(vaddr, e) => handle_exception(bits_of(vaddr), e)`) — **not** `veda_trap()`/`trap()` (those return `ExecutionResult`, consumed by the normal per-instruction execute dispatch, a different, incompatible calling context from this fetch-time hook).
- **A genuinely important negative finding**: `xret_callback : (bool) -> unit`, the only hook fired specifically on MRET/SRET (`model/core/callbacks.sail`, called from `execute MRET()` in `model/extensions/I/base_insts.sail`), is declared **`pure {cpp: "xret_callback"}`** — a C++-emulator-instrumentation hook (matching `fetch_callback`/`mem_read_callback`/etc., all similarly `pure`+`cpp:`-tagged for external tracing/RVFI use), **not** a real Sail-level architectural-state extension point. Sail's own effect system would reject a register write inside it. There is no real, non-pure hook that fires specifically on xRET. Editing `base_insts.sail`'s own `execute MRET()` clause directly was ruled out — it would violate this project's own already-established, deliberate boundary (`FORMAL_VERIFICATION_PLAN.md`'s own decision to build via `model/extensions/Veda/` rather than fork/modify the base model).
- **The real, correct alternative, found by checking `core/csr_begin.sail`**: `read_CSR`/`write_CSR`/`is_CSR_accessible`/`csr_name_map` are all declared `scattered function`/`scattered mapping` — the exact same additive-clause mechanism this project's own `encdec`/`assembly`/`execute` (every Veda-Core instruction so far) already uses. New CSR addresses can be added with a real `function clause read_CSR`/`write_CSR` in `veda_regs.sail`, accessible via the real, unmodified, already-working base-ISA `CSRRW`/`CSRRS` — no new instruction, no hook into MRET needed at all.

**This resolves the entry/exit save-restore question differently than Section 6's first draft assumed**: rather than *automatic* hardware save-on-trap-entry and restore-on-MRET, the design below makes restoration an **explicit software action** — the trap handler reads the saved bounds back via ordinary `csrr`/`csrw` and writes them into the live PCC CSRs itself, before its own `mret`. This is not a compromise forced by a missing feature; it is *consistent* with a convention this project's trap model already established in Milestone 9: advancing `mepc` past the faulting instruction before `mret` is already an explicit, required software step (RTL's own `veda_smoke_m9.S`: `addi t3, t3, 4; csrw mepc, t3` before `mret`) — nothing in this design is automatic that wasn't already explicit for `mepc` itself.

**Real CSR addresses**: RISC-V spec (`riscv-spec.pdf`, Table 91, "Allocation of RISC-V CSR address ranges," p.664) reserves `0x7C0`–`0x7FF` as the real, standard **Machine-level "Custom read/write"** range — verified directly, not invented, the same real precedent this project already leaned on once for `mtvec`/`mepc`/`mcause`/`mtval` sitting in the *standard* M-mode range (`0x300`-`0x3FF`) just above it. Four new CSRs, all in the real custom range: `veda_pcc_base = 0x7C0`, `veda_pcc_length = 0x7C1`, `veda_mepcc_base = 0x7C2`, `veda_mepcc_length = 0x7C3`.

## 6. Proposed design

**New persistent architectural state** (Sail: two new registers, mirroring `veda_oda`/`veda_oda_tag`'s own precedent from Milestone 11; RTL: two new persistent signals, mirroring `$mtvec`/`$mepc`'s own precedent from Milestone 9):

- `veda_pcc_base : bits(32)`, `veda_pcc_length : bits(16)` — the currently-active compartment bounds.
- `VEDA_PCC_UNBOUNDED`: `Length = 0xFFFF` (all-ones) is the sentinel for "no compartment currently active — ordinary, unconstrained execution," matching real CHERI's own convention that a machine boots with an "almighty" root capability and only ever *narrows* from there. Reset value is unbounded — this design adds zero new constraint to any code that never calls `OCInvoke`, by construction.
- `veda_mepcc_base`/`veda_mepcc_length` — the saved compartment bounds across a trap, the direct structural twin of `mepc` alongside `mepcc` (matching real CHERI's own "Exception Program Counter Capability" naming and role exactly).

**Narrowing**: `OCInvoke`'s own existing success path gains one real side effect — `veda_pcc_base := cs1.Base`, `veda_pcc_length := cs1.Length` (the code capability's own bounds become the new compartment). No new instruction is needed for *return*: real CHERI's own convention (and this project's own already-built `OCInvoke`) treats invocation as symmetric — a callee holding a valid sealed return-code-capability (however software chooses to hand one out, already outside this ISA's own concern, exactly as real CHERI leaves it to software/compiler convention) calls `OCInvoke` again to return, which narrows (or widens back to unbounded, if the return capability's own `Length` is `0xFFFF`) `veda_pcc_*` exactly the same way.

**Enforcement (Sail)**: override `ext_fetch_check_pc(start_pc, pc)` to return `Some(())` whenever `veda_pcc_length != VEDA_PCC_UNBOUNDED` and `pc` falls outside `[veda_pcc_base, veda_pcc_base + zero_extend(veda_pcc_length))`; override `ext_handle_fetch_check_error(())` to save-and-reset (below) then call `handle_exception(zero_extend(5'b10000 @ 0b00001), E_Extension(()))` directly — cause `0b00001` (`0x01`, Bounds/Length Violation, already active, reused per Section 5) with `cap_idx = 0b10000` (16, the new PCC sentinel), built inline rather than through `veda_trap()`'s own 4-bit-`vcapidx`-typed interface (Section 5a) since this case was never a real capability-register index to begin with.

**Enforcement (RTL)**, once the Sail side is verified: a new, unconditional, every-cycle check — distinct in kind from every other check in this file so far, which are all gated on a specific decoded opcode — `$veda_pcc_violation = (veda_pcc_length != VEDA_PCC_UNBOUNDED) && !(pc_within[veda_pcc_base, veda_pcc_base+veda_pcc_length))`, joining the same `$veda_trap_taken` family Milestone 9 already built, with the identical `cause`/`cap_idx` values chosen above.

**Exception entry**: `veda_trap()` (the function every existing Veda-Core hard-trap already calls) gains one real new line before its own `trap(...)` call — save `veda_mepcc_* := veda_pcc_*`, then reset `veda_pcc_* := VEDA_PCC_UNBOUNDED` (matching real CHERI's own "Exception Code Capability" requirement, Section 4: a trap handler must run in a trusted, unbounded context). The new PCC-violation path (Section 5a, routed through `handle_exception` directly rather than `veda_trap()`) performs the identical save-and-reset inline, via a small shared helper both call.

**Exception exit — explicit, software-driven, not automatic** (Section 5a's own real finding): the trap handler, before its own `mret`, reads `veda_mepcc_base`/`veda_mepcc_length` (CSRs `0x7C2`/`0x7C3`) and writes them into `veda_pcc_base`/`veda_pcc_length` (CSRs `0x7C0`/`0x7C1`) — four ordinary `csrr`/`csrw` instructions, the same real, already-established convention as `mepc`'s own explicit pre-`mret` advancement (Milestone 9).

## 7. Deliberately out of scope for this design, named rather than silently dropped

- **`Perms` on PCC** (e.g., a real `Permit_Execute`-on-PCC check distinct from the capability-register-level `Permit_Execute` `OCInvoke` already checks on its *operand* before entry): real CHERI does track PCC permissions, but nothing in this project's own current instruction set would exercise a PCC-level permission distinct from what `OCInvoke`'s own entry check (Milestone 10, cause `0x11`/`0x19`) already covers once. Adding it now would be unused surface area — deferred until a real consumer exists.
- **Any base-ISA-wide fetch capability check**: explicitly rejected in Section 2, not merely postponed — this is the central rescoping decision of this document.
- **A real distinguishable `cap_idx` sentinel for every future "not a real capability register" case**: this design claims exactly one sentinel value (16, matching CHERI's own `PCC_IDX`); if a future feature needs its own, that is that feature's own decision to make, not preemptively reserved here.

## 8. Sequencing

Sail first, then RTL — the same order and reasoning already established and followed for every prior milestone in this project. Concretely, now grounded in Section 5a's own verified real hooks rather than assumed ones: (1) add `veda_pcc_base`/`veda_pcc_length`/`veda_mepcc_base`/`veda_mepcc_length` registers, `VEDA_PCC_UNBOUNDED`, and a shared `veda_pcc_save_and_reset()` helper to `veda_regs.sail`; (2) add `function clause read_CSR`/`write_CSR`/`is_CSR_accessible`/`csr_name_map` clauses for the four new `0x7C0`-`0x7C3` addresses; (3) override `ext_fetch_check_pc`/`ext_handle_fetch_check_error` in a new `veda_regs.sail` (or a new `veda_pcc.sail`) section, per Section 5a/6 above — **no change to `veda_trap`/`veda_xtval`'s own existing `vcapidx`-typed interface needed**, the PCC sentinel is built inline instead; (4) extend `VEDA_OCINVOKE`'s own success path in `veda_cap_insts.sail` to set `veda_pcc_base/_length := cs1.Base/cs1.Length`; (5) call `veda_pcc_save_and_reset()` from inside `veda_trap()` itself (`veda_bind_insts.sail`); (6) write Sail self-check tests (a positive compartment-bounded-jump-succeeds case, a negative escape-attempt-traps case using the `0x01`/`cap_idx=16` encoding, and a trap-inside-compartment case proving the explicit CSR-based save/restore round-trips correctly across a real `mret`); (7) full Sail regression; (8) only then begin the RTL mirror, following the identical Sail-verified design (RTL's own `MHARTID`-style fixed constants and the already-built `$veda_trap_taken` family make the RTL side mostly a mechanical port once Sail is right, per past milestones' own experience — but not attempted until Sail is fully green).
